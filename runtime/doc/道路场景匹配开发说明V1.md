| 项目 | 位置 |
|------|------|
| C++ 源码 | `/home/cpk/road_segment_test_service/src/main.cpp` |
| C++ 构建目录 | `/home/cpk/road_segment_test_service/build` |

特征服务监听 `19001`，负责 LoMa Top-2 特征匹配。

## 2. 场景数据结构

每个相机使用独立目录：

```text
scene/
└── 7543/
    ├── scene_01.jpg
    ├── scene_02.jpg
    └── distance_map.json
```

`distance_map.json`：

```json
{
  "scene_01.jpg": {
    "result": "1",
    "direction": "向上上行、向下下行",
    "distances": [
      {"y": 520, "distance": 50},
      {"y": 680, "distance": 30}
    ]
  }
}
```

规则：

- `result` 为输入端定义的 `0`、`1`、`2`，不根据文件名判断。
- `direction` 只有两个枚举：`向上上行、向下下行`、`向上下行、向下上行`。
- 每张图片独立维护自己的方向、结果和多组 Y 坐标距离。
- Y 坐标原点位于图片左上角，向下增大。

## 3. 数据维护逻辑

### 上传或覆盖

```http
POST /api/test/highway_scene_image
```

请求使用 `multipart/form-data`：

- `data`：包含 `camera_id`、`image`、`result`、`direction`、`distances`。
- `image`：图片二进制文件。

同一 `camera_id + image` 再次上传时：

1. 覆盖原图片。
2. 覆盖该图片在 `distance_map.json` 中的全部配置。
3. 清除该图片的内存缓存。

图片和 JSON 均通过临时文件写入后原子替换。

### 删除

```http
DELETE /api/test/highway_scene_image?camera_id=<camera_id>&image=<image>
```

删除流程：

1. 校验相机编号和图片名，禁止目录穿越。
2. 删除指定图片文件。
3. 删除 `distance_map.json` 中同名配置。
4. 清除该图片的内存缓存。
5. 图片不存在时返回 `404`。

### 查询

```http
GET /api/test/highway_scene_images
GET /api/test/highway_scene_images?camera_id=<camera_id>
```

无 `camera_id` 时返回相机总数、图片总数和各相机维护数量。

带 `camera_id` 时返回该相机的全部图片及每张图片的结果、方向和距离数组。

## 4. 匹配逻辑

```http
POST /api/test/highway_road_match
```

当前处理流程：

1. 接收客户实时图片和 `camera_id`。
2. 调用 `19001` Hybrid 特征服务。
3. DINOv3 对该相机全部基准图进行粗排。
4. LoMa 对 DINOv3 Top-2 候选进行局部特征和几何匹配。
5. 综合分最高且达到阈值时，确定最佳图片。
6. 从最佳图片对应的 `distance_map.json` 读取 `result`、`direction` 和 `distances`。
7. 返回最佳图片名、Hybrid 特征总分和图片维护信息。

道路轮廓接口 `/api/test/highway_road_segment` 已移除，匹配流程不再调用道路分割服务，也不再计算道路 IoU。

简化输出：

```json
{
  "status_code": 200,
  "msg": null,
  "data": {
    "camera_id": "7543",
    "result": "1",
    "best_image": "scene_01.jpg",
    "total_score": 0.92,
    "direction": "向上上行、向下下行",
    "distances": [
      {"y": 520, "distance": 50},
      {"y": 680, "distance": 30}
    ]
  }
}
```

字段来源：

| 字段 | 来源 |
|------|------|
| `best_image` | Hybrid 特征匹配的最佳基准图 |
| `total_score` | Hybrid 特征综合得分 |
| `result` | 最佳图片上传时维护的值 |
| `direction` | 最佳图片上传时维护的值 |
| `distances` | 最佳图片上传时维护的距离数组 |

## 5. 响应记录

每次接口响应都会单独归档，上传、删除、查询和场景匹配使用不同的响应类型名称。

排查时先查看运行配置中的响应归档目录，再按接口类型和时间定位单次 JSON 响应。

## 6. 编译与部署

编译：

```bash
cmake --build /home/cpk/road_segment_test_service/build -j2
```

替换程序前先备份当前二进制，然后执行：

```bash
install -m 0755 \
  /home/cpk/road_segment_test_service/build/road_segment_test_service \
  /opt/RoadSegmentTestService/RoadSegmentTestService

/opt/RoadSegmentTestService/startRoadSegmentTestService restart
```

检查：

```bash
curl http://127.0.0.1:19000/ping
curl http://127.0.0.1:19001/ping
systemctl status road-segment-feature.service
```

正常结果：主服务返回 `pong`，特征服务状态为 `active`。

## 7. 修改注意事项

- 新增图片元数据时，同时修改上传、查询、删除、匹配输出和两份接口协议。
- 不要重新使用图片名前缀推断 `result`。
- 删除或覆盖图片后必须清除对应缓存。
- 修改匹配算法时保持特征服务返回候选图片名与场景目录文件名一致。
- 正式部署前使用专用测试相机编号完成上传、查询、匹配、删除闭环测试。
