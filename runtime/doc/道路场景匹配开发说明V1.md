# 道路场景匹配开发说明（V1）

## 1. 运行结构

| 项目 | 位置 |
|------|------|
| C++ 源码 | `/home/cpk/road_segment_test_service/src/main.cpp` |
| C++ 构建目录 | `/home/cpk/road_segment_test_service/build` |
| 正式运行目录 | `/opt/RoadSegmentTestService` |
| 主程序 | `/opt/RoadSegmentTestService/RoadSegmentTestService` |
| 特征服务 | `/opt/RoadSegmentTestService/feature_service.py` |
| 场景查询接口 | `http://10.88.4.37:9091/api/oauth/v3/marker/calibration/highway_scene_images` |
| 接口协议 | `/opt/RoadSegmentTestService/doc/` |

主服务监听 `19000`，负责 HTTP 接口、道路轮廓比对、调用特征服务和结果汇总。

特征服务监听 `19001`，负责 LoMa Top-2 特征匹配。

## 2. 场景数据来源

匹配时按 `camera_id` 调用 9091 标定接口。接口返回图片本地绝对路径及配置：

```json
{
{
  "id": "29751949712753701",
  "imagePath": "/mnt/data/sda/oauth/images/.../scene.jpg",
    "result": "1",
    "direction": "向上上行-向下下行",
    "distances": [
      {"y": 520, "distance": 50},
      {"y": 680, "distance": 30}
    ]
}
```

规则：

- `result` 为输入端定义的 `0`、`1`、`2`，不根据文件名判断。
- `direction` 只有两个枚举：`向上上行、向下下行`、`向上下行、向下上行`。
- 每张图片由 9091 标定服务独立维护方向、结果和多组 Y 坐标距离。
- Y 坐标原点位于图片左上角，向下增大。

## 3. 数据维护逻辑

本服务不提供场景图片上传、删除和查询接口，不维护 `scene` 目录。

图片及标定数据统一由 9091 标定服务维护。本服务只在匹配请求到达时实时查询，并直接读取返回的 `imagePath`。

9091 查询失败时最多重试 5 次，采用递增短间隔；全部失败后匹配接口返回 JSON 错误。

匹配阈值只允许通过正式机配置维护，请求 JSON 中的阈值字段不会生效：

```text
MATCH_THRESHOLD=0.70
ROAD_MATCH_THRESHOLD=0.90
```

`startRoadSegmentTestService` 必须显式导出这两个变量后再启动主程序。

## 4. 匹配逻辑

```http
POST /api/test/highway_road_match
```

当前处理流程：

1. 接收客户实时图片和 `camera_id`。
2. 特征服务调用 9091 接口查询该相机基准图。
3. DINOv3 粗排，LoMa 对 Top-2 做局部特征和几何匹配。
4. 主服务对实时图和特征最佳场景图调用道路分割服务并计算 IoU。
5. 特征和道路均达到阈值时，直接使用原始距离标定。
6. 特征达到阈值但道路未达到阈值时，对每个原始 Y 上下各 100 像素内的 LoMa 匹配点进行 Y 重标定。
7. 重标定至少保留 2 个顺序一致的有效距离点，否则返回 `no_match`。

道路轮廓独立 HTTP API `/api/test/highway_road_segment` 仍不对外开放；道路分割只在匹配流程内部调用。

简化输出：

```json
{
  "status_code": 200,
  "msg": null,
  "data": {
    "camera_id": "7543",
    "result": "1",
    "best_image": "scene_01.jpg",
    "total_score": 0.92,
    "direction": "向上上行、向下下行",
    "distances": [
      {"y": 520, "distance": 50},
      {"y": 680, "distance": 30}
    ]
  }
}
```

字段来源：

| 字段 | 来源 |
|------|------|
| `MatchId` | 9091 中最佳图片对应的标定记录 ID |
| `best_image` | Hybrid 特征匹配的最佳基准图 |
| `total_score` | Hybrid 特征综合得分 |
| `road_score` | 实时图与最佳场景图的道路轮廓 IoU |
| `match_mode` | `road_feature_direct`、`feature_recalibrated` 或 `no_match` |
| `result` | 最佳图片上传时维护的值 |
| `direction` | 最佳图片上传时维护的值 |
| `distances` | 最佳图片上传时维护的距离数组 |

## 5. 响应记录

每次响应单独归档 JSON 的功能由 `RESPONSE_ARCHIVE_ENABLED` 控制，正式环境当前设置为 `0`，仅保留业务运行日志。

## 6. 编译与部署

编译：

```bash
cmake --build /home/cpk/road_segment_test_service/build -j2
```

替换程序前先备份当前二进制，然后执行：

```bash
install -m 0755 \
  /home/cpk/road_segment_test_service/build/road_segment_test_service \
  /opt/RoadSegmentTestService/RoadSegmentTestService

/opt/RoadSegmentTestService/startRoadSegmentTestService restart
```

检查：

```bash
curl http://127.0.0.1:19000/ping
curl http://127.0.0.1:19001/ping
systemctl status road-segment-feature.service
```

正常结果：主服务返回 `pong`，特征服务状态为 `active`。

## 7. 修改注意事项

- 新增图片元数据时，同时修改上传、查询、删除、匹配输出和两份接口协议。
- 不要重新使用图片名前缀推断 `result`。
- 删除或覆盖图片后必须清除对应缓存。
- 修改匹配算法时保持特征服务返回候选图片名与场景目录文件名一致。
- 正式部署前使用专用测试相机编号完成上传、查询、匹配、删除闭环测试。
